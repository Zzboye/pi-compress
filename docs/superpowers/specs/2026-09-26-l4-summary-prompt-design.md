# L4 摘要 prompt 重写（V6：条目化 + 保留标识）

日期：2026-09-26
状态：已实施
范围：`src/prompts.ts` 的 `buildIntentOutcomePrompt`（L3→L4 的 `compressEnds` 用）

## 1. 背景：旧 prompt 的「≤20/≤30 字」是一个不存在的契约

旧 prompt（V0）：

```
规则：
1. userIntent：用户这轮想要什么，≤20 字，动宾短语
2. outcome：模型最终达成了什么结论/结果，≤30 字，写结论不写过程
```

问题有三层：

**① 模型不遵守。** 171 条真实 L4 产出的统计：

| | 平均 | 最大 | 超限率 |
|---|---|---|---|
| intent | 20.2 字 | 85 字 | 57/171 = 33% |
| outcome | 44.1 字 | 160 字 | 95/171 = 56% |

代码侧也没有任何长度校验（`compressEnds` 只查 `typeof === "string"`），所以「≤30 字」纯属 prompt 里的装饰。

**② 遵守的那部分是有害的。** 字数限制的代价是**丢掉识别性信息**——文件名、commit hash、测试数字。实测对比同一 turn：

| | V0（≤30 字） | 不限字数 |
|---|---|---|
| outcome | `导出了LLM实际收到的27条消息逐字原文并保存至指定文件` | `导出了LLM实际收到的27条消息逐字原文（64,202字符）并保存至指定文件` |
| outcome | `审查完成：需修复1项，实现者偏差说法成立` | `报告判定规格大体符合、需修复1项Important（跨会话ID复用）…` |

**③ 它是 L5 描述质量差的一个隐藏原因。** `mergeDescribe` 的输入就是 L4 渲染文本——喂进去的是被砍过的空洞结论，产出自然是废话。

## 2. 探针：8 组 prompt 变体

语料：本项目真实会话（277 个 turn），摘要模型 `deepseek-v4-flash`，temperature=0。
完整逐条结果见附件：
- `docs/evidence/l4-summary-prompts-compare.txt`（V0–V7，8 样本）
- `docs/evidence/l4-v6-v9-v10-compare.txt`（V6/V9/V10，8 样本）

指标定义：**压缩率** = (intent + outcome) 字符 / (用户消息 + 回复) 字符（越低压缩越狠）；**标识保留率** = 摘要中出现的「文件名:行号 / commit hash / 测试数字」占原文此类项的比例。

| 变体 | prompt 核心手段 | 压缩率 | 标识保留率 | outcome 平均 |
|---|---|---|---|---|
| V0 | 硬字数（≤20/≤30） | 1.3–3.6% | **0%** | 35 字 |
| V1 | 只删字数限制 | — | — | 67 字 |
| V2 | 「读者不必回看原文」+ 要素列举 | — | — | **572 字** |
| V3 | V2 + 「宁可写长」 | — | — | **791 字** |
| V4 | 区间指引（20-60 / 40-120） | 9.4–16.0% | 13–21% | 246 字 |
| V5 | 条目化（结论/参数/限制/待办） | 19.5% | 29% | 400 字 |
| **V6** | **条目化 + 保留列表结构** | **22.2%** | **52%** | **681 字** |
| V7 | 条目化 + 固定顺序 | 21.5% | 42% | 562 字 |
| V9 | V6 + 条目上限 + intent 约束 | 10.6% | 24% | 308 字 |
| V10 | V6 + intent 约束 | 9.4% | 26% | 290 字 |

## 3. 裁定

**采纳 V6。**

三条关键证据：

**① V0 的 1.3% 压缩率是「虚高」的**——它不是压得好，是把定位信息压没了。压缩率必须与保留率一起看：V6 用 22% 的体积换来 52% 的保留率，是这批变体里性价比最高的。

**② 修正版（V9/V10）反而更差，失败机制值得记录。** 我试图在 V6 基础上加两条「优化」——「每条只写判定+定位，删掉解释、依据、复述」和「findings 超过 3-4 条时只详列 3-4 条」。结果保留率从 52% 掉到 24%。原因：

> **在审查报告语境里，「定位」和「解释」混在同一句里**，模型执行「删掉解释」时把 `fab5831`（commit）、`src/recall.ts`（文件）一起删了。
>
> V6 之所以保住定位，靠的是「**保留这些条目**」+「**不要合并成一段总述**」这两句"笨"指令——它不给模型取舍的裁量权。一旦给了裁量权（哪怕是同义改写），模型就会删掉它认为不重要的部分，而它判断"重要性"的标准与定位价值无关。

**③ V2/V3 的爆炸说明措辞极度敏感**：V2 只比 V4 多了一句「让读者不必回看原文」，outcome 从 145 字炸到 572 字。任何暗示「信息要全」的措辞都会被放大成信息抽取。V6 的剔除项（「剔除：重复描述、背景科普、举例、客套话、过程叙述」）是必要防线。

## 4. 实施

`buildIntentOutcomePrompt` 替换为 V6 文案，与探针逐字一致。

记录一个**探针数据的口径修正**（避免后续误读）：

- 全量 277 条「回复」中，**代码/标识覆盖字符占比加权平均 37.7%**
- 但按回复类型分层后差异很大：**SDD 子代理报告 43%**（Verdict/Findings/file:line/Evidence 命令输出），**对话回复 24%**（纯代码块+行内代码）
- 且「最长回复」全是子代理报告——**按长度取样的分布是偏的**。V6 相对 V4 的收益在子代理报告上最大，在纯讨论 turn 上收窄（样本 3 是讨论类：V4 173 字 / V6 438 字，V6 的四个分类标签是纯开销）

**这个偏差不推翻裁定**（V6 在报告类场景的收益是真实的，而报告类占 L4 的多数），但记录在此：如果后续发现讨论类 turn 占比上升导致 L4 体积失控，可考虑「按回复类型分流」——但那是**代码侧检测**（如回复是否含 findings 结构），不是 prompt 能可靠表达的（V8 试过用 prompt 让模型自己判断类型，效果不佳）。

## 5. 影响

| | V0 | V6 |
|---|---|---|
| L4 单 turn 渲染 | 44.6 tok | **约 150–160 tok**（+3 倍） |
| 触发 40k 阈值所需 turn 数 | ≈900 条 | **≈260 条** |

副作用是**更早触发降级瀑布**——好处是 L4 不会膨胀，代价是 L5 更早介入。与 task-009（L5 固定步长分组）有交互，实施 L5 改动时需以新体积重新核算。

## 6. 非目标

- **不加代码侧长度截断/护栏**：探针里 V6 最长的 outcome 是 1233 字（无失控），而护栏会在数据侧制造新的静默丢失。字数问题已由「废除硬上限」解决。
- **不做「L4 短形式压缩」**（如 `329 passed/1 skipped` → `329P/1S`）：实测的冗余主要是 Evidence 段与「已核查通过」清单，那属于**回复侧**的冗余，应在摘要前就由 prompt 的剔除项覆盖（V6 已覆盖）。代码侧格式替换收益未验证，不做。
- **不改 `mergeDescribe` / `buildSummarizePrompt`**：本次只动 `buildIntentOutcomePrompt`。
